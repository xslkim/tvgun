## 1. 总体判断

**v0.2 已经解决了 v0.1 评审的全部 P1 问题，可以开始 A0（旧基准录制）。A1 开工前还需要处理三件事：A1 拆成两步、通用核心补上空间查询、统一“发布姿态”的定义。**

新版做得好的地方：

- **v0.1 评审的意见基本都被准确吸收，并有超出原意见的补充。** 例如命中时刻协议（§5.3 L160–170）区分了逻辑发布、渲染提交和真实显示，并且不默认启用回溯，比 v0.1 评审 R02 的建议更严谨。
- **差异登记补上了 v0.1 评审漏掉的问题。** 已复核属实：D08 纸身误伤会扣生命（`alley_rules.gd` L207–208 调用 `damage`），与 `gameplay_constraints.json` 的“只扣分”冲突；D06 获救动作片段实际时长为 2.2 秒（`rescued_bounce.json` 的 `duration`），代码按 2.3 秒切换。
- **A0 明确要求先录旧基准，再改运行循环**（L381），并区分了“允许的 ±1 tick 误差”和“有意修复的缺陷”。
- **通用性有可运行的验收标准**（§10.1）。要求用异题材白模实际编译、运行、回放、生成候选，而不是“字段可扩展”就算通用。“设计表达/编译/运行/审阅/验证”五层支持状态的要求（L430）也很实用。
- **调研移到附录后，正文篇幅更集中。** 附录新增的三款游戏标注了手册页码和证据边界。

新风险主要来自范围扩大：用户把目标明确为跨游戏引擎之后，A1 承担的工作量大幅增加，而通用核心的“声明式条件/效果”清单还不足以表达《纸灯城》的第一个机制。

优先级约定同 v0.1 评审：**P1** 为对应阶段开工前应在方案中解决；**P2** 为该阶段实施中补齐即可。

## 3. 新发现的问题

### N01 · P1：A1 应拆成“只改运行循环”和“改数据模型”两步

**位置：** §11 A1 L385–390、A2 L394–396。

**问题：** 现在的 A1 同时包含：固定步长、输入队列、命中几何与绘制分离、逻辑层判定、状态序列化、轨迹哈希、两个游戏的 schema 子集、D01–D10 迁移、bible 引用、ID 键集合、毫秒量化、包清单、能力检查和性能目标。再加上 A2 要求异题材白模可运行，实际上 A1 要完成通用核心的首版，并把《纸灯城》改写为规则包。

如果这些改动一起完成后再与 A0 基准比较，一旦结果不一致，就无法判断是运行循环、数据模型、规则包改写还是缺陷修复造成的。

**建议：** 按“每步只改一类东西”拆成等价链：

1. **A1a 确定性改造：** 保留现有 `alley_rules.gd`/`alley_scene.gd` 的玩法语义，只改固定步长、输入队列、命中几何与绘制分离、软化判定移到逻辑层（D10）、轨迹输出。与 A0 基准比较，允许预先登记的 ±1 tick 误差。
2. **A1b 缺陷修复：** 单独修复 D02、D08 等已决定修复的项，每项都对应一条预期的轨迹差异。
3. **A1c 通用核心与规则包：** 建立最小核心，把《纸灯城》迁移为规则包，并加入抽象靶场。此时与 A1b 的轨迹逐 tick **精确一致**，不再需要任何误差容忍。

这样每一步的差异都有唯一来源，A1c 的“完全一致”也能直接证明通用化没有改变玩法。

### N02 · P1：通用核心的条件与效果缺少空间查询，《纸灯城》的第一个机制就无法声明式表达

**位置：** §4.1 L103、§2.1 D10 L57。

**问题：** §4.1 规定条件“只读取有类型的状态与事件”，效果限于改状态/资源、产生事件、增删实体、启停行为、切换受击许可、播放 cue。但“墨鸦在灯光范围内才软化”取决于墨鸦当前位置与灯光遮罩的关系，D10 也写明要用已冻结贴图采样作为逻辑输入。这是空间查询，不在上述清单里。保护区、目标间距、可见面积、“进入某区域触发”等也同理。

如果不补，这个机制只能写成插件；《纸灯城》的第一个招牌机制就绕开了“常规组合用声明式数据”的原则，抽象靶场也会遇到“目标进入射击区才计时”之类的需求。

**建议：** 在设备与表现适配层定义一组空间派生状态，由逻辑步根据已发布姿态计算，并写入轨迹：区域包含、遮罩采样值、两对象距离或重叠面积、可见面积比例。条件可以读取这些派生状态，例如“`crow_01` 在 `lamp_01.light_mask` 中的采样值 ≥ 0.3”。这些查询的算法版本、采样点定义（中心点还是命中区）和阈值来源都要登记，审阅工具也能直接显示。

### N03 · P1：“发布姿态”和“已提交渲染的姿态”需要统一定义

**位置：** §5.3 L162、L164、L168；A1 L387。

**问题：** 新版用了几个相近的说法：L162 说命中用“最近一次已提交渲染的权威姿态快照”，L164 说每个逻辑 tick 末尾“发布新姿态”，L168 和 A1 又提到“发布步表”和“绘制只消费发布快照”。逻辑每个 tick 都发布一次，而渲染以自己的帧率提交：144Hz 时同一姿态被画多次，30Hz 时会跳过某些 tick。命中到底绑定哪一个，目前要靠读者推断。

**建议：** 在 §5.3 加一个简短术语表，并写清以下几点：

- 逻辑每 tick 发布一个带编号的姿态快照，保留最近 N 个（环形缓冲，N 由回溯上限决定）。
- 渲染每帧记录自己实际提交的快照编号。
- 输入入队时绑定“渲染最近一次提交的快照编号”。
- 无窗口模拟时，“提交”由指定的发布步表模拟。

### N04 · P2：明确“已采用版本”与 Git 中关卡源文件的关系

**位置：** §7.3 L275–279、A2 L394。

**问题：** 新版写了“源数据入 Git”，又写了“候选存于按清单哈希命名的不可变目录”和“独立索引记录当前采用版本”。但没说清楚：Git 中的关卡源文件是否就等于当前采用版本？Agent 是改 Git 工作区，还是只写候选目录？用户采用时，是否把候选内容写回源路径并提交？候选目录本身是否入库？如果候选源不入库，回退依赖一个不受版本管理的目录；如果编译产物和证据（截图、短片）也入库，仓库会迅速膨胀。

**建议：** 候选的源文件体积小，入 Git；编译产物可由源文件和锁定的编译器重建，证据单独归档，二者都不入 Git。采用操作是一次提交，内容包括更新采用指针，或把候选源写回规范路径。Agent 只写候选，不直接改规范路径。补丁的 base revision 默认指向当前采用版本的清单哈希。

### N05 · P2：区分核心术语和《纸灯城》示例，避免 Agent 把示例当成核心字段

**位置：** §5.2 L143–145、§5.4 L176、§5.5 L186、§5.7 L208、§8.1 L290、§8.2 L303、§9.2 L334–336。

**问题：** §4.1 规定核心“不得引用 g01、墨、纸、灯或具体角色名”，但第 5–9 节仍大量使用本作词汇描述通用模型：可伤害区写“墨身、保护纸身”，实例配置写“净化次数、硬化条件”，任务写“净化数量、救援、点灯”，语义事件示例是 `ink.purified`、`resident.rescued`，快照清单含“灯光渐变”，公平性边界写“临近灯灭、居民遮挡”。§5.2 第 1 项还把 1920×1080 白框写成通用规则，而 §4.1 L99 已说明它属于 TVGun 配置。

Agent 会把这些规范当作 schema 的依据来读，很可能直接把 `ink.purified` 写进核心事件名。

**建议：** 加一张“核心术语 → g01 规则包映射”表，例如：`target.neutralized` 在 g01 中叫“净墨”，`activation_source` 在 g01 中是灯，`protected_zone` 在 g01 中是纸身。正文用核心术语，本作例子统一标注为“g01 示例”。§5.2 第 1 项改为“由设备适配声明，TVGun 默认值为……”。

### N06 · P2：明确会话外壳与 HUD 的归属，并迁移 F1 调试层

**位置：** §4.1 L96–107、A2 L394。

**问题一：会话外壳没有归属。** 标题、暂停、续关、结算等流程状态目前在 `alley_rules.gd` 的 `phase` 中，界面绘制在 `alley_scene.gd` 的 `_draw_hud()`。`main.gd` 实际依赖的是 `model.tick/command/snapshot/user_paused` 这组隐含接口，而 `build_0b.py` 把单一游戏的脚本复制成 `game_rules.gd`/`game_scene.gd`。四层边界中没有说明这些外壳流程和 HUD 属于哪一层。抽象靶场“无生命、只有得分”，正好需要不同的外壳。

**问题二：F1 调试层只是起点。** 它在 g01 的场景脚本里，换游戏就没有了；而且画的是外接矩形，不是实际 alpha 命中形状，用来解释“这一枪为何没中”可能产生误导。

**建议：** 把“会话流程（标题/暂停/续关/结算）+ HUD”定义为通用外壳，由规则包提供参数和内容；把 `main.gd` 依赖的隐含接口写成正式契约。A2 的调试预览把命中叠加层移到适配层，绘制实际 alpha 区域和辅助吸附范围。

### N07 · P2：A0 录制需要隔离实时输入，并记录步进序列

**位置：** §11 A0 L381。

**问题：** 冻结模式下 `_process` 仍会轮询光枪链路并在光枪模式下分发事件（`main.gd` L161–163），鼠标点击也会经 `_unhandled_input` 直接触发射击。录制期间若误触鼠标或手机仍在连接，基准就会被污染。另外，调试接口的 `step` 一次推进多帧后才刷新画面（L365–367），输入只能注入在两次 `step` 之间，因此输入时刻的精度等于步进粒度。例如复现 D02 需要先步进 9 帧（0.15 秒）再射击。

**建议：** 录制时关闭鼠标、UDP、HTTP 实时输入源，或在冻结模式下屏蔽它们；基准文件记录完整的步进与注入序列，保证可重放。

### N08 · P2：为扩大后的范围补充粗略规模和阶段止损点

**位置：** §11。

**问题：** v0.2 增加了四层架构、插件契约、两个白模包和六项覆盖走查，但各阶段没有规模估计，也没有“不达标时怎么办”的决策点。之前的 GunForge 评审已经指出，没有实测返工量时，排期容易失真。

**建议：** 每个阶段给出粗略规模（例如以天或周为量级），并设置止损点：A1a 后如果确定性改造的成本远超预期，重新评估回放需求；A2 迭代两三轮后，由用户决定继续进入 B，还是先补规则能力。估计值标为初估即可。

## 4. 可直接整理的一致性问题

1. **点灯差异重复描述。** §2 L42 的点灯 6 秒/8 秒段落与 §2.1 D01 内容重复，保留 D01 即可。
2. **“静态不可达”的范围。** §9.1 L327 把“必需目标静态不可达”列为阻止编译。条件依赖空间派生状态（N02）时无法静态判定，建议写成“可静态证明不可达”；其余情况归入启发式警告。
3. **相对时间的量化顺序。** §5.3 L156 规定出现时间向上取整、截止向下取整。建议补一句：相对时间先在毫秒域换算成绝对时间，再统一量化，不逐段取整，避免链式依赖累积误差。
4. **D02 的修复范围。** D02 写“确认具体影响后再实施”，而 §12 L419 建议直接修复。建议统一为：A1b 先用调试接口复现，再修复。
5. **抽象靶场的启用时间。** §10.1 L370 说 A2 必须运行，A1 的 schema 子集也包含它。建议在 A1c 验收中明确写上“抽象靶场可编译运行”，否则 A2 开始时才发现缺口。
