# 《关卡设计引擎与可视化审阅工具方案》评审意见

评审日期：2026-11-08
评审对象：`LEVEL_DESIGN_ENGINE_PLAN.md` v0.1（需求讨论稿）
评审方式：全文阅读，并对照现有实现核对第 2 节“现状”描述及各项设计在现有架构上的落地难度。

本次只交付评审意见，没有修改原方案，也没有开发引擎或工具。下文行号对应本次读取的版本；后续修改后以章节和问题编号定位。

## 1. 总体判断

**方向正确，边界清楚，可以作为需求基线；但在进入阶段 A 前，需要补一项被低估的地基工作，并调整阶段顺序。**

值得保留的部分：

- **已确认边界收得紧。** 只做《纸灯城》2D 定点站位、工具只读加批注、AI 产出候选版且必须由用户采用，这三条把范围控制在可交付的规模内。
- **“同一个编译产物”原则正确。** §4 L122 明确审阅工具不另写命中和战斗逻辑，避免出现“工具里看着对、游戏里不对”。
- **打击范围拆成六层。** §5.2 把可见区、可伤害区、辅助命中、设备可达性分开，比单一 radius 更接近光枪的真实问题。现有 `hit_resolver.gd` 已经做到辅助不产生弱点奖励（L31–34 把 `weak` 改为 `primary`），与方案一致。
- **诚实标注证据级别。** 调研部分区分“公开机制”和“引擎提炼”，难度部分承认机器人未经玩家数据标定，不宣称数学证明可解。
- **第 2 节现状描述基本属实。** 抽查确认：`alley_0b.json` 只有三轮时间和规则数值；墨鸦中心、居民位置、灯罩区域写死在 `alley_scene.gd`；`build_0b.py` L51 的公平性检查是固定 2.25 秒动作成本加顺序不重叠判断。

主要风险有两个：

1. **确定性回放是方案中多项能力的共同前提，但现有运行循环不是确定性的，方案没有把改造它列为独立工作项。** 时间跳转、多 seed 机器人、同输入对齐、“解释某一枪为何命中”都依赖它（见 R01–R03）。
2. **最有价值的“AI 修改 → 用户审阅 → 再修改”闭环放在最后一个实施阶段才验证。** 成本最高的网页审阅工具排在它前面，而工具形态本身还没确定（见 R05）。

优先级约定：**P1** 为阶段 A 开工前应在方案中解决的问题；**P2** 为对应阶段实施前应补齐的问题。

## 2. 优先解决的问题

### R01 · P1：把“确定性固定步长运行”列为阶段 A 的第一项工作

**位置：** §5.3 L153、§8.2 L277、§9.3、§11 阶段 A L332–336。

**现状证据：**

- 逻辑按渲染帧的可变时长推进：`main.gd` L166 `advance(minf(delta,.1))`，规则内部以浮点累加计时（`alley_rules.gd` L115 `clock += dt`）。
- 输入不在逻辑步内处理：鼠标在 `_unhandled_input`（`main.gd` L227 起）、光枪在 `_process` 开头（L161–163）即时调用 `dispatch`，没有按 tick 排队。
- **命中几何由渲染代码生成。** `alley_scene.gd` 的 `update_frame()`（L105–209）在绘制时同时构建 `hit_items`，`dispatch` 直接用它判定（`main.gd` L201）。
- **“墨鸦是否已软化、可受伤”由渲染层决定。** `alley_scene.gd` L171–176 在墨鸦中心采样灯光溢出贴图得到 `light_exposure`，再据此给贴图标 `primary` 或 `invalid`；规则层的 `light_active()`（`alley_rules.gd` L79–80）定义了另一个阈值，但没有被使用。同一条玩法规则有两个定义，权威一方在表现层。
- 已有基础：调试接口的 `freeze/step/input`（`main.gd` L360–373）能以 1/60 秒步进并注入输入，可以作为改造起点。

**影响：** 不改造的话，时间跳转无法重现同一状态；批量模拟必须真实渲染，无法快于实时运行；审阅工具显示的命中区和实际判定可能来自不同时刻；阶段 A 的“同输入对齐”也没有可比较的基准。

**建议：** 在阶段 A 最前面加一个子阶段，完成以下改造后再迁移数据：

1. 逻辑改为固定步长加累加器，渲染只读取逻辑状态并做插值。
2. 所有输入进入带 tick 戳、会话和序号的队列，在逻辑步内统一消费。
3. 把“姿态与命中几何计算”从“绘制”中拆出，变成逻辑状态和 tick 的纯函数，可在无窗口模式下运行。
4. “可伤害/硬化/受保护”等判定状态只由逻辑层产生，渲染和审阅叠加层都只读它。
5. 输出逐 tick 的事件轨迹及其哈希，用于回归比较。

**验收：** 同一关卡、seed 和输入记录，在无窗口模式下连续运行三次轨迹哈希一致；渲染帧率分别锁定在 30/60/144 时轨迹不变；78 秒关卡的无窗口模拟耗时有明确目标（建议至少 10 倍实时，具体数值待测后确定）。

### R02 · P1：明确命中按玩家“看到的那一帧”判定，而不是本 tick 刚更新的位置

**位置：** §5.3 L157。

**问题：** 方案的同 tick 裁决顺序是“先更新已有对象的位置与命中姿态，再处理输入命中”。这意味着一枪会针对玩家尚未看到的新位置判定。玩家瞄准的是已经显示的画面，光枪链路还有手机处理、网络和显示延迟。现有代码反而更接近“按已显示画面判定”，因为 `dispatch` 使用的是上一次 `update_frame` 生成的 `hit_items`。

静止目标影响很小，但 §3.8 列出的俯冲、横穿、投射物等运动目标会直接受影响。若渲染帧率高于 60Hz 并做插值，“看到的位置”和“逻辑位置”也会出现差异。

**建议：** 在时钟规则中写清：命中以输入 tick 时最近一次已发布的姿态判定；是否允许按设备延迟回溯若干 tick，以及回溯上限是多少。插值只影响画面，不进入命中计算。公平性检查和难度机器人使用同一套定义。

**验收：** 增加“目标在两 tick 间移出准星”“延迟回溯边界”“截止 tick 当帧命中”等用例，结果写入 §5.3 的边界用例集。

### R03 · P1：旧 Demo 对齐验收需要先建立可比较的基准

**位置：** §11 阶段 A L336。

**问题：** 验收要求“同 seed/同输入时，波次、判定、资源、获救与结算对齐”，但现有 Demo 没有输入录制，时序依赖实际帧时长，因此不存在“同输入”下的旧版结果。此外，浮点累加与整数 tick 的阈值比较可能相差一帧：以 1/60 秒累加 180 次未必恰好不小于 3.0，`clock>=enemy.at` 可能晚一帧成立。

**建议：** 迁移前先用现有调试接口在冻结模式下以 1/60 秒步进、注入脚本化输入，录制旧版的事件序列作为基准。对齐按事件级比较，并写明允许的误差（如 ±1 tick）。基准用例至少覆盖：正常通关、每波漏打一只、误伤居民、空弹换弹、失锁暂停与恢复、续关。

### R04 · P1：样例 schema 与“按 ID 定位”和补丁机制相互冲突，时间单位也应调整

**位置：** §5.1、§6 L207、L218–220、§7.3 L253。

**问题一：数组与稳定 ID。** 样例中 `entities` 和 `events` 是数组。§7.3 建议采用 JSON Patch 风格，而 JSON Patch 的路径是数组下标（如 `/events/3/trigger`），这与 §5.1“不靠数组下标定位”矛盾。插入或删除一项会让后续补丁和批注路径整体错位。

**问题二：作者数据用 tick。** 样例写 `at_tick: 180`、`delay_ticks: 30`，但 §5.3 也说 60Hz 尚待确认。用户批注、Agent 推理和设计说明都以秒为单位。如果源数据存 tick，将来改 tick 频率就要迁移所有关卡，Agent 还要反复换算。

**问题三：多文件版本。** §6 建议拆成多个文件，§7.3 的 base revision 却是单个值。

**建议：**

- 需要稳定定位的集合用“以 ID 为键的对象”存储，例如 `"events": {"spawn_01": {...}}`。这样 JSON Pointer 路径天然是 `/events/spawn_01/trigger`，补丁和批注都不依赖顺序。确实需要顺序时用显式的 `order` 字段。
- 源数据用秒（或整数毫秒），编译器按明确的取整规则转换为 tick，运行包和 source map 保存 tick。
- 版本号定义为整个关卡包的清单哈希（所有源文件路径加内容哈希），补丁的 base revision 指向这个清单。

### R05 · P1：调整阶段顺序，先用最低成本验证 AI 修改闭环

**位置：** §4 L122、§11 阶段 B–C、§12 问题 3 和 5。

**问题：** 方案的核心价值是“AI 改、用户看、批注、再改”。按现有顺序，这个闭环要在阶段 C 才第一次跑通，而在此之前要完成成本最大的阶段 B：网页时间轴、事件图、版本对照，再加 Godot 桥接。桥接方式（内嵌、并排、单窗口）留到原型阶段决定，但这恰恰是阶段 B 工作量的主要变量。

此外，阶段 A 要“冻结首版 schema”，而 §5 描述的是覆盖 Boss、分支、剧情、道具的完整模型。只用一个 78 秒、每波两只墨鸦的站点来冻结这么大的 schema，容易设计出用不到或用错的字段。2026-11-02 评审 R06 也提出过同样的建议：先从真实需求提取，再泛化。

**建议：** 改为纵向切片：

1. **阶段 A：** R01 的确定性改造，加 Demo 数据化。schema 只冻结 Demo 和下一个新遭遇实际需要的字段；其余机制在能力目录中登记为“预留、不可运行”，构建时明确拒绝。
2. **简化版闭环：** 关卡源文件由 Agent 直接修改；候选版本存为独立目录或提交；差异用文本加关键帧截图；预览直接用 Godot 加调试叠加层（现有 F1 调试图层可以扩展出命中区、槽位和简单时间刻度）；批注先在聊天中用“版本 + 秒数 + 对象 ID + 描述”表达。和用户实际迭代两三轮。
3. **阶段 B：** 根据上一步暴露的真实痛点，再决定网页工具的范围和桥接方式。

如果维持网页加 Godot 双窗口的推荐方案，建议在阶段 B 前做一两天的技术验证，比较“Godot 内置审阅界面”和“网页加桥接”两种形态。Godot 方案省掉了桥接和状态同步，网页方案更适合文本差异和批注管理。

### R06 · P1：现状差异只登记了一项，实际还有几处规则缺陷和数据冲突

**位置：** §2 L40、§5.6 L183–185。

方案只登记了点灯 6 秒与 8 秒的差异。核对代码后，至少还有以下几项需要在迁移前决定“保留现状、修复，还是交给用户决定”：

1. **获救后可以重复计分（代码路径推断，未实机复现）。** 获救动画 `rescued_bounce` 在前 0.2 秒内仍显示居民身上的墨（`vendor/clips/rescued_bounce.json` 的 `attachment_keys.rescue_ink`），这块墨仍是 `primary` 可命中目标（`puppet.gd` L67）。规则层命中 `resident_ink` 时没有检查是否已获救，每次都重置 `rescued_at` 并加 300 分（`alley_rules.gd` L187–190）。射击间隔是 0.15 秒，小于 0.2 秒，所以连续射击可以反复得分，并让获救动画不断重新开始。这说明“获救”这类状态切换要在逻辑层一次完成，不能依赖动画隐藏命中区来保证。
2. **灯已亮时再打灯仍加分并续时。** `alley_rules.gd` L183–186 每打中一次灯都加 25 分并重置亮灯时间。这既可以刷分，也让“灯能否再次点亮、是否允许续时”成了隐含规则。方案 §12 问题 7 只问了 6 秒还是 8 秒，应把这一点加进去。
3. **槽位和敌人尺寸与已有设定不一致。** `bible/prototype_slot_schedule.json` 规定敌人 200px、候选槽位中心 (420,350)/(1110,350)、居民附近禁用槽位，并注明“engine enforcement pending”。运行时墨鸦固定在 (1320,550)，按 264px 绘制（`alley_scene.gd` L170、L177）。两者可能采用不同坐标系，但至少需要登记并确认哪一份是准的。
4. **预警光环半径不一致。** `bible/warning_contract.json` 规定光环半径 17–26 内容像素、1.5Hz；运行时绘制半径 22–30（`alley_scene.gd` L278–279）。频率一致，半径不一致。
5. **其他写死在代码里的关卡内容。** 拾取物类型按波次奇偶切换（`alley_rules.gd` L198–205），灯罩墨迹按 `wave%3` 选图（`alley_scene.gd` L142），获救动画按 2.3 秒写死（L156–158）。第 3 项方案已提到，前两项没有。

方案 §5.6 L183 写“救援完成后连续射击不再触发纸身误伤”，现有代码其实已经做到了（获救后纸身不再标为 `protected`）。真正缺的是上面第 1 项的重复计分问题。

**建议：** 阶段 A 交付一张“现状差异与缺陷登记表”，每项写明来源、现状行为、处理方式（保留/修复/待用户决定）。迁移只在标为“保留”的项上复刻旧行为；对齐验收中的“已知数值差异”就引用这张表。

### R07 · P1：说明新的“设定约束/能力目录”与现有 `bible/` 文件的关系

**位置：** §4、§5.8、§7.1。

**问题：** `games/g01/bible/` 已经有 `gameplay_constraints.json`（人类不是敌人、纸身只扣分）、`warning_contract.json`、`animation_contract.json`（可救援动画、命中遮罩规则）和 `prototype_slot_schedule.json`（槽位与禁用位置）。它们正是方案所说的“设定约束”和“能力目录”的一部分，但方案没有提到。如果新建一套能力目录而不引用它们，就会出现第三份数据源；R06 第 3、4 项说明已经存在漂移。

**建议：** 方案中列出现有 `bible/` 文件分别对应哪类约束；能力目录引用这些文件及其版本，而不是复制其中的数值；校验器直接读取它们。像 `prototype_slot_schedule.json` 这种注明“引擎执行待定”的约束，应当成为阶段 A 校验器的首批规则。

## 3. 对应阶段实施前应补齐的问题

### R08 · P2：定义 Agent 如何“看到”关卡，把常见视觉批注变成可自检的指标

**位置：** §7.1 L235、§7.2、§8.3。

**问题：** 方案例子中的批注（“墨鸦挡住居民胸口”）是视觉问题。Agent 无法观看实时画面，如果只能读 JSON，就只能猜测改动是否解决了问题，只能把验证工作全部交还用户。

**建议：**

- 规定每个候选版本自动生成的证据包：关键事件 tick 的截图（含命中区叠加和不含叠加各一张）、轨迹摘要、检查结果。
- 把高频批注类型逐步转成自动指标，例如：必打目标的可见面积比例、敌人与居民可救墨区的遮挡比例、同屏有效威胁数、事件空档时长、最小目标尺寸、内容区亮度。Agent 修改后先自检这些指标，再提交候选。
- 给出批注包的最小字段：批注 ID、版本、站点、时间区间（秒）、对象 ID、画面区域、文字、严重程度、期望结果、不可改变项、截图路径。
- 批注状态建议增加“需澄清”，让 Agent 在无法判断用户意图时退回提问，而不是猜一个改法。

### R09 · P2：区分“阻止构建”的结构错误和“需要确认”的启发式判断

**位置：** §9.1、§9.2。

**问题：** §9.1 把“设备不支持的必需动作”“在不可见状态造成不可避免伤害”列为阻止构建，但 §9.2 承认可辨识时刻和可解性只能保守估计、不能证明。启发式检查若直接阻止构建，误报会卡住 Agent 迭代，或诱导 Agent 为了通过检查器而修改关卡，而不是为了设计意图修改。

**建议：** 只有确定性的结构问题才阻止构建，如引用缺失、类型或单位错误、死循环、等待节点无超时、NPC 被设为攻击者、保护区登记为可伤害。公平性和可辨识性一类结果标为错误级警告，候选版本可以生成和预览，但采用前用户必须逐条确认。

### R10 · P2：确定版本存储方式，候选预览不能覆盖已采用版本

**位置：** §7.3 L255、§11 阶段 C。

**问题：** 方案定义了候选状态机，但没有说明存在哪里。现有构建流程只有一个输出目录：`build_0b.py` L43 把关卡复制为 `framework/runtime/level.json`，L44–46 还把游戏脚本复制进去。预览候选版本如果走这条路径，会覆盖当前采用版本的运行包。

**建议：** 优先复用 git：关卡源文件入库，候选版本是不可变目录或提交，另用一个索引文件记录状态和“当前采用版本”指针；批注以文件形式引用版本哈希。运行时支持通过参数加载指定版本的编译产物，候选预览和已采用版本并存。状态机中 `previewed` 由谁、在什么动作下写入也需要说明（打开预览即算，还是用户显式标记）。

### R11 · P2：时间跳转需要性能指标和完整的快照清单

**位置：** §8.2 L277、§11 阶段 B 验收。

**建议：** 补充快照间隔、跳转延迟目标（例如 90 秒关卡内任意跳转不超过 0.3 秒，数值待原型确认），以及快照必须包含的表现相关状态：木偶动画的片段与时间、镜头晃动相位（现为 `view_clock = model.total`，`main.gd` L186）、灯光渐变量、提示文字计时、拾取物状态。阶段 B 验收中的“对齐画面”应定义为同 tick 截图逐像素一致，或给出允许的误差。

### R12 · P2：精简文档结构，并标明哪些待确认问题会阻塞阶段 A

**位置：** §3、§12。

**建议：**
