# 《通用关卡设计引擎开发任务》评审意见

评审日期：2026-11-08
评审对象：`LEVEL_DESIGN_ENGINE_TASKS.md` v0.1（对照 `LEVEL_DESIGN_ENGINE_PLAN.md` v0.3）
评审方式：逐项检查任务与方案的一致性、依赖关系、验收的可执行性，并对照现有代码、测试和 Android 客户端，确认任务是否遗漏了会受影响的现有行为。

本次只交付评审意见，没有修改任务文档、方案或代码，也没有开始任何开发任务。下文行号对应本次读取的任务文档版本；问题编号为 T01 起。

## 1. 总体判断

**任务文档忠实地落实了方案 v0.3，阶段门、止损规则和证据要求都很扎实。A0（LD00–LD03）补上命中几何基准和锁定状态注入后即可授权；A1a（LD04–LD06）开工前，还需要处理输入队列对现有协议的影响、现有回归测试的归属，以及“逐 tick 精确一致”的数值定义。**

做得好的地方：

- **等价链清楚。** A1a 只改确定性、A1b 只修缺陷、A1c 才通用化，每步都有可比较的基准，“未通过”时只允许在本阶段内定位（L136、L153、L191）。这正是 v0.2 复审 N01 的意图。
- **止损规则不降低目标。** L80 明确止损时不能删掉第二个白模、绕过统一运行器或改为只播视频，避免以“缩减范围”为名悄悄放弃泛化。
- **证据要求具体。** §2.3 要求记录变更文件、命令与退出状态、预期失败的拒绝原因；A0 要求两次受控运行验证稳定性，D02 未复现时如实登记（L111）。
- **规模初估有边界说明。** 明确不含等待用户和硬件的时间，并规定达到上限时交由用户决定（L78）。
- **N01–N08 的追踪表（§15）准确。** 抽查各项都能在对应任务中找到落实内容。

优先级约定：**P1** 为对应任务开工前应在任务文档中解决的问题；**P2** 为执行过程中补齐即可。

## 2. 优先解决的问题

### T01 · P1：LD04 的输入队列会改变 HTTP 射击和调试接口的同步返回语义，手机端依赖这一点

**位置：** LD04 L118–121；LD02 L101–104。

**现状证据：**

- `main.gd` L213–225 的 `http_command` 在处理 `SHOT` 时立即分发，并在同一次调用里返回 `hit: model.hits > before` 和当前分数。
- Android 客户端的 HTTP 射击模式依赖这个同步结果：`MainActivity.java` L1374–1398 读取响应中的 `hit` 来决定命中/未命中闪光和震动，并用 `score` 更新屏幕分数。
- 调试接口的 `input`（`main.gd` L368–373）同样立即返回分发后的状态；现有机器人 `qa_0b.py` L69–81 在每次射击后立刻断言墨鸦状态和弹药数。

**问题：** LD04 要求“所有输入排队，调试输入走同一消费路径”。输入改为在下一个逻辑步消费后，HTTP 响应如果仍在入队时返回，`hit` 永远是 false，手机就会对每一枪都显示“未命中”；`qa_0b.py` 也会失败。任务文档只提到“旧包时效、去重与 LOST 屏障不退化”（L121），没有覆盖这类同步返回语义。

**建议：** 在 LD04 中明确两种接口的新语义：

- **HTTP 射击：** 入队后延迟回复，等消费该输入的逻辑步完成后再返回原有字段。现有 `_process` 的顺序是先轮询 HTTP、再推进逻辑，同一帧内即可完成回复。如果决定改变响应格式，就按协议变更处理：升级协议版本、重建 APK，并按 `WORKFLOW.md` 核对版本号。
- **调试接口：** `input` 返回入队回执（含序号），结果在后续 `step` 后读取；或者新增“注入并推进到消费完成”的操作。`qa_0b.py` 按新语义同步更新；旧版脚本随 LD01 的旧实现快照一起保存，作为基准工具。

**验收：** Android HTTP 模式下命中与未命中的闪光、震动和分数显示正确；`qa_0b_http.py`、`qa_0b_udp.py` 通过；调试接口的语义变更写入技术契约。

### T02 · P1：把现有回归测试纳入各验收门

**位置：** §2.3 L42–48；G1a L135、G1c L190。

**问题：** 仓库已有多套测试，0B 报告也引用了它们的结果：`framework/tests/core_tests.gd`（39 项核心检查，覆盖坐标、保护区/遮挡/吸附、旧包时效、会话、失锁暂停、校准、换弹和续关）、`qa_0b.py`（实际运行中的三轮通关和死亡续关）、`qa_0b_http.py`、`qa_0b_udp.py`、`qa_frame_geometry.py`，以及追踪器的旧版回归。任务文档没有提到其中任何一项。A1a 改运行循环和命中几何、A1c 改主入口接口时，这些测试最可能先暴露问题。

**建议：** 在 §2.3 或各验收门中列出必须保持通过的现有测试。如果某项测试的语义因设计有意改变（如 T01 的同步返回），应记录测试如何迁移，而不是删除或跳过。

### T03 · P1：A0 基准要覆盖命中几何，并能注入锁定状态

**位置：** LD02 L101–104、LD03 L108–112、LD05 L125–128。

**问题一：基准用例缺少命中几何覆盖。** LD03 的用例都是玩法流程，现有机器人也只瞄准每个目标的中心点（`qa_0b.py` 的 `shoot` 使用 `targets` 中的瞄点）。而 LD05 要重写的恰恰是几何部分：alpha 边缘、15 像素辅助吸附、吸附路径上的保护区和前景阻断、硬化区域，以及镜头晃动下的移动位置。只用中心点射击的基准，无法证明 LD05 的几何等价。

**问题二：录制无法注入锁定状态。** LD03 要录“失锁恢复”，LD02 要求“设备锁定/会话状态也由受控记录驱动”。但现有 `locked()` 在鼠标模式下恒为 true（`main.gd` L156–157），调试接口也没有设置锁定状态的操作。这个控制必须由 LD02 的插桩补丁新增，任务文档没有点明。

**建议：**

- LD02 的插桩补丁增加两个只读或受控操作：一是锁定状态覆盖；二是“命中采样”，即用当前 `hit_items` 和原有解析器对一组给定点求命中结果，不触发射击、不改变状态。
- LD03 增加“命中采样网格”用例：在若干代表时刻（墨鸦硬化与软化、居民挣扎中与获救动画前 0.2 秒、拾取物出现、镜头晃动的极值位置），对内容区按固定间距采样，并在目标边缘和保护区附近加密，记录每个点的 `id`、`kind` 和 `assisted`。
- LD05 的验收加上“命中采样网格与 A0 逐点一致”。

### T04 · P1：“逐 tick 精确一致”需要先定义连续数值如何比较

**位置：** §2.3 L46、LD06 L133–135、LD12 L183。

**问题：** LD12 要求 g01 迁移后与 G1b 的公共行为轨迹逐 tick 精确一致，比较范围包括区域值和姿态。这些都是浮点数：灯光渐变用 `move_toward` 逐步累加（`alley_rules.gd` L120），镜头晃动来自正弦函数（`alley_scene.gd` L109–110），软化判定是贴图采样值乘以灯光强度（L175）。声明式核心即使公式等价，运算顺序不同也会在末位产生差异；如果差异恰好落在 0.3 阈值附近，离散结果会翻转。到时候很容易为了通过对照而事后放宽容差，这正是任务文档禁止的。§2.3 提到“固定数字编码”，但没有定义连续值的比较方式。

**建议：** 在 LD06 的轨迹 schema 中定义规范编码：

- 离散字段（事件、tick、资源、状态、命中结果）严格相等。
- 连续字段按声明的分辨率量化后比较，例如姿态量化到 1/64 像素、渐变量量化到 1/4096。
- 影响玩法判定的连续量（灯光强度、阈值比较），最好在 A1a 就改为整数或定点运算，让 A1c 的核心沿用同一种算法，从根源上避免浮点差异。

这不是放宽容差：离散结果仍然必须精确一致，只是让“精确”有明确定义。

### T05 · P1：标明哪些检查由用户执行、哪些由 Agent 执行

**位置：** §2.3 L44、LD03 L109、LD16 L212、LD22 L260。

**问题：** 任务由 Agent 执行，但有些检查 Agent 做不到或不该自己做：§2.3 要求“实际试听代表片段”，Agent 无法听声音；LD03 要求“人工抽查输入与画面”，没有说明“人工”指用户，还是读取截图的 Agent。如果不明确，这些检查要么卡住任务，要么被 Agent 以不可靠的方式“完成”。

**建议：** 每项检查标注执行者：

- **Agent 可做：** 读取截图、核对 cue 时间轴、检查音频文件是否存在、分析音量包络与 cue 是否对齐。
- **必须由用户做：** 实际试听、手感和真机体验。

用户检查集中安排在 G0、G2、G4 等验收门，避免每个任务都等待用户。

## 3. 执行中应补齐的问题

### T06 · P2：阶段顺序与任务依赖不一致，G2 后的分支路径也没有对应任务

**位置：** §4 L64、LD20 L245、LD21 L252、LD16 L215。

§4 的顺序写成 B 完成后才到 C，但 LD20 只依赖 G2、LD10、LD15（仅工具内展示依赖 G3），LD21 依赖 LD20，所以 C 的前两项在 G2 后就可以开始。另外，G2 的决策点允许用户选择“先补规则能力”，但没有说明这种情况下执行哪些任务。

**建议：** 写明单条工作流按顺序执行；如果用户在 G2 选择先补规则能力，就把 LD20–LD21 提到 LD17–LD19 之前，LD22 仍需要 G3。

### T07 · P2：高风险的大任务需要内部检查点，A1c 的估计偏紧

**位置：** LD05 L125–128、LD10 L166–169、LD12 L180–183、LD19、§4 L73。

LD05、LD10、LD12、LD19 各自包含很多相互独立的部分。以 LD12 为例，如果把时序、空间、救援与计分、cue 一次全部迁移后再对照，一旦不一致就很难定位。

**建议：**

- **LD05 拆为：** 姿态与几何纯函数（以 T03 的采样网格验收）；提交、绑定与缓冲；D10 搬到逻辑层。
- **LD12 按子系统逐个迁移：** 依次迁移出现时序、空间源与受击许可、救援与计分、cue 和转场，每迁移一个子系统就与 G1b 轨迹对照一次。

LD12 的精确对照是整条任务链最大的进度风险。A1c 的 8–15 日包含了编译器、核心、外壳、g01 迁移和靶场五项工作，建议在 G1a 后重新估算时，把 LD12 单独列出。

### T08 · P2：Agent 的提交要与用户未提交的工作隔离

**位置：** §2.3 L48、LD14 L198–200。

任务文档已禁止 `git add .`，这很好。还需要再具体一些：用户可能已经把自己的改动加入暂存区，Agent 提交时不能把它们一起带进去。

**建议：** 候选与采用提交使用只包含指定路径的提交方式（`git commit --only -- <路径>`）；提交前检查本次差异只涉及允许的目录；不自动推送；说明候选提交直接放在当前分支，还是放在专用分支。

### T09 · P2：外部证据目录需要保留与清理策略

**位置：** §2.2 L38。

每个候选都会生成截图、短片和完整轨迹，A2 迭代几轮后数据量增长很快。建议定义保留范围（已采用版本、最近 N 个候选、未关闭批注引用的证据），在报告中输出目录占用，并说明证据被清理后审阅工具如何显示（LD23 已要求“丢失外部证据可检测”）。

### T10 · P2：指定由哪个任务建设资源与能力目录

**位置：** LD00 L85–86、LD09 L161、LD16 L212；方案 §5.8。

LD16 要求 Agent “读取能力”，方案 §5.8 要求 Agent 不能编造资源 ID。但没有任务负责建立 Agent 所读的资源目录，即带哈希和约束的站点、槽位、角色、动画、音效清单。LD00 的“能力覆盖清单”和 LD09 的“支持状态清单”描述的是引擎能力，不是资源。

**建议：** 由 LD12（g01）和 LD13（靶场）分别产出资源目录，验收加上“引用目录外的资源 ID 时构建失败”。

### T11 · P2：任务状态只保留一个来源

**位置：** §2.1 L25、LD00 L86。

§2.1 说任务状态记录在本文件中，LD00 又要产出“阶段状态记录”，两处容易不同步。建议只保留一处，例如 `reviews/` 下的状态文件，本文件只链接它；或者反过来，只在本文件中维护状态表。

## 5. 评审证据与边界

本次全文阅读了任务文档，对照了方案 v0.3 的 §4.3、§4.4、§11、§12，以及 `WORKFLOW.md`。代码方面复核了 `main.gd`（`http_command`、调试接口的 `input` 与 `step`、`locked()`）、`MainActivity.java`（HTTP 射击对 `hit` 和 `score` 的使用）、`qa_0b.py`（射击后立即断言的写法）、`alley_rules.gd` 与 `alley_scene.gd`（浮点渐变、晃动和采样），以及 `.gitignore` 与 `.gitattributes`（`runtime/` 被忽略，PNG/MP4 走 LFS）。

本次没有运行 Godot、现有测试或 Android 客户端。T01 关于“入队后返回会使 `hit` 恒为 false”是根据代码顺序推断的；T07 中对估计偏紧的判断是经验判断，不是测算结果。
