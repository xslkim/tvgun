## 0. 如何使用本文档

1. 先通读全文，再执行第 3 节「阶段 0」。
2. 每个阶段都有 **输入 / 动作 / 产出 / 通过门槛（Gate）**。未通过 Gate 不得进入下一阶段（除非按第 13 节的规则降级处理并记录）。
3. 过程记录分工明确，避免多处重复维护：
   - `docs/DECISIONS.md` 记录长期有效的决策、假设与理由；
   - `PROGRESS.md` 只记录当前状态、阻塞项和下一步，涉及决策时链接到 DECISIONS；
   - 具体的失败过程写在对应的 QA 报告和 `troubleshooting.md` 中。
4. 本文档中标注「（需核实）」的信息，是撰写时的已知情况，可能已过时。你必须用联网检索核实后再依赖它。
5. 关于**工具的客观技术事实**（功能、格式、版本、授权条款），如果本文档与官方资料冲突，以官方资料为准，并在 `DECISIONS.md` 中记录。但本文档规定的**目标、交付物和验收标准**不会因为外部资料而改变。
6. 本文档中的规则分为三级：**硬约束**（必须满足，违反即不通过）、**软约束**（应当满足，偏离时需写明理由）、**建议**（推荐做法，可按实际情况取舍）。没有标注的条目按软约束处理。

### 0.1 哪些是固定的，哪些可以自由发挥

本文档的大部分内容，是帮你少走弯路的**参考方案**，不是唯一做法。

**固定不变**（只有这几类）：

- 第 1 节的任务目标与交付物；
- 第 13 节的验收等级；
- 标为【硬】的质量约束：关节不反折、骨长不变、脚不滑步、循环无接缝等；
- 证据优先、不得伪造、遵守许可证；
- 2.1 的自主决策边界。

**可以替换或改进**（只需在 DECISIONS.md 写明理由，并且结果仍满足上面的固定项）：

- 工具与模型选择，包括本文档没有提到的新工具；
- 生图、拆件、绑骨、动画的具体方法。例如，你发现了比「拆件 + 手动关键帧」更好的整体方案，就可以采用；

- 默认值、参考阈值和各项数字；
- Demo 的具体角色和设计。

**鼓励**：主动寻找比本文档更好的做法。如果某条规定在实践中明显妨碍质量或效率，记录原因后调整它，不要为了合规而机械执行。

## 1. 任务目标

建立一套 **可复用、可持续** 的 2D 游戏角色/怪物生产管线，并用实际 Demo 证明它可行。管线包含三部分：

- **美术资源由 AI 文生图生产**：角色与怪物的设计稿，以及拆好部件、可以直接绑骨骼的分层素材。
- **骨骼动画**：素材绑定骨骼后制作各类动画。动画中**不允许出现任何违反常识的关节动作**，比如肘、膝反折，关节转过生理极限，脚底滑步，肢体突然跳变。
- **规范与方法论沉淀**：最终形成完整的规范文档、方法论，以及可被后续 AI Agent 直接调用的 Skill（含脚本、模板、检查器），供后续游戏项目持续使用。

### 1.1 最终交付物（Definition of Done）

| 编号 | 交付物 | 说明 |
|---|---|---|
| D1 | 调研报告 `docs/research/` | 现有工作流、骨骼动画工具、AI 生图/拆层/绑骨工具的全面调研与对比，带引用链接 |
| D2 | 选型决策 `docs/DECISIONS.md` | 选定的主管线与备选管线，以及理由 |

| D4 | 骨骼绑定规范 `docs/spec/RIG_SPEC.md` | 各类原型（人形、四足、飞行、多足、软体等）的标准骨架、命名、关节角度限制表、IK 规则 |

| D10 | 总结报告 `docs/FINAL_REPORT.md` | 成果、质量评分、已知限制、后续建议 |

## 2. 约束与基本原则

1. **可自动化优先**：你很可能无法熟练操作 GUI 软件。选工具时，优先考虑满足以下任一条件的方案：
   - 动画数据格式公开且文档化（如 JSON），可以用脚本直接生成或修改；
   - 有命令行导出或无头渲染能力；
   - 有开源运行时，能在脚本里渲染预览帧。
   如果确需 GUI，可以尝试桌面自动化，但它只能作为辅助手段，不能成为管线的关键依赖。
2. **授权合规**：本项目只用于**非商业目的**，包括美术生产、技术研究与演示。
   - 不要求工具、模型、素材具备商用授权。仅限非商用的工具和模型都可以使用。
   - 必须遵守各自的许可证和服务条款，特别是对下载、修改、展示、再分发的限制。
   - 每个工具、模型、素材都要记录许可证，以便以后对外发布 Demo 或 Skill 时核对。
   - 不得使用受版权保护的现有角色形象作为生成目标。
   - 无法确认授权时，标记为「风险」，继续推进，不要因此停下来。
3. **可追溯、尽量可复现**：
   - **结果可追溯（硬约束）**：保存原始输出、模型及版本、Prompt、种子、参数、参考输入。动画保留源数据与生成脚本，不要只留成品。
   - **流程可复现（软约束）**：保存工作流、脚本、依赖版本。云端或闭源服务的输出本身就不确定，记录下来即可，不要为了逐像素复现反复重试。
4. **证据优先**：任何「已完成」「质量合格」的结论，都必须附带验证产物，即质检报告、预览视频或截图。
5. **不得伪造**：调研中找不到的信息写「未找到」，不要编造工具功能、版本号或论文。

### 2.1 自主决策边界

你需要**自主完成绝大多数决策**，不要因为等待人类而停工。

**可以自主决定的事项**：工具选型、风格细节、角色设计、骨架设计、阈值校准、Demo 角色选择。规则是：优先采用下面的默认值；如果调研或实践表明有更好的选择，可以改，但要写入 DECISIONS.md。

**默认值**：

| 项目 | 默认值 |
|---|---|
| 游戏类型与视角 | 横版 2D 动作游戏；角色为 3/4 侧视，默认面朝右（向左由运行时镜像） |
| 美术风格 | 卡通风格，约 3–4 头身，有描边，赛璐璐上色，光源统一在左上方 |
| 角色基准高度 | 512px（从脚底到头顶，不含武器）；大型怪物与 Boss 按设定比例放大 |
| 帧率 | 30fps，数据以秒为单位 |
| 位移方式（Root Motion） | 项目默认原地动画；冲刺、扑击等动作可以在单个动画中声明使用根骨位移 |
| 坐标约定 | y 轴向上，单位为像素，角度单位为度，逆时针为正 |

**必须请求人类的情况**（仅限以下几种）：

- 需要付费、购买授权、注册或登录账号、提供 API Key；
- 关键依赖的授权存在不确定性，而且找不到替代方案；
- 所有备选方案都失败，导致连第 13 节规定的最低交付范围都无法达成。

请求时，同时继续推进不受阻塞的工作。如果长时间得不到回复，就改用免费/开源方案继续，并记录这一降级。

## 5. 阶段 1：全面调研

### 5.0 调研深度分级与停止条件

调研要「广而分级」，不要求每个工具都做同样深度：

- **核心候选**（每个方向选 2–4 个）：填写完整调研卡片（附录 A），并做动手小测试，例如能否用脚本生成或读取它的数据、能否渲染出预览。
- **其他工具**：在简表中各写一行，说明功能定位，以及为什么不列为核心候选，就足够了。

**停止条件**：满足以下三点即可结束阶段 1，进入选型。

1. 核心候选已完成可执行性验证；
2. 各候选之间的关键差异已经清楚；
3. 主要风险（授权、自动化能力）都有证据支撑。

后续阶段发现新工具时，追加到调研报告即可，不需要回到阶段 1 重新调研。

### 5.1 调研范围（每一项都要过一遍，深度按 5.0 分级）

**A. 2D 骨骼动画工具与运行时**（核心候选需调研：功能、数据格式、是否支持网格变形/权重/IK/路径约束/蒙皮、命令行与自动化能力、运行时与引擎支持、授权与价格、社区活跃度、最后更新时间）。最低清单如下：

- Spine（Esoteric Software）
- DragonBones
- Spriter Pro
- Creature
- Live2D Cubism：偏变形器体系，评估它是否适合游戏战斗角色
- Rive
- Moho
- Toon Boom Harmony
- Godot 4 的 2D 骨骼体系：Skeleton2D / Bone2D / Polygon2D 权重 / AnimationPlayer / 2D IK
- Unity 2D Animation + PSD Importer + 2D IK
- Cocos Creator 的骨骼动画支持
- Blender 用于 2D 切片动画的插件或方案（如 COA Tools 类，需核实现状）
- 其他在检索中发现的、截至执行日期近两年新出现的工具

**B. AI 美术资源生产**

- 文生图模型与平台：SDXL 系、Flux 系、Qwen-Image 等开源模型，以及主流闭源服务。重点记录：风格一致性能力、透明背景能力、许可证。
- 角色一致性手段：LoRA 训练、IP-Adapter / 参考图控制、角色三视图/设定图工作流、种子与 Prompt 固定策略。
- 姿势与构图控制：ControlNet（OpenPose / Depth / Lineart 等）、用标准 T/A-pose 骨架图约束出图。
- 透明图层与拆件：
  - 透明背景生成（如 LayerDiffuse 类方案）；
  - 自动分层/分图层生成模型（如 Qwen-Image-Layered 等，需核实）；
  - 分割（SAM / SAM2 等）；
  - 抠图（rembg、BiRefNet 等）；
  - 局部重绘（inpainting）补全被遮挡部位。
- ComfyUI 生态中与「角色拆件」「Spine 素材」相关的现成工作流与节点。

**C. AI 辅助绑骨与动画**

- 自动绑骨/自动动画：Meta Animated Drawings（开源）等。也要检索截至执行日期近两年的新研究与商用工具，关键词见 5.3。
- 视频/动捕 → 2D 骨骼：MediaPipe、DWPose、OpenPose 等姿态估计，用于从真人参考视频提取关节角度曲线。
- 2D 角色动画相关论文（arXiv）及其开源代码。

**D. 成熟工作流与行业实践**

- 商业 2D 游戏（如采用 Spine 的手游/独立游戏）的角色拆件规范、骨架规范公开分享。
- 官方教程、GDC 演讲、工作室技术博客中的切件与绑定规范（关节处重叠区、隐藏面补画、网格密度等）。
- 经典动画原理资料：动画十二法则、走跑循环关键姿势、打击感（预备—打击—停顿—恢复）。

### 5.2 资源查找方法

1. **一手来源优先**：官方文档 > 官方 GitHub / Release Notes > 官方论坛 > 知名从业者的博客/视频 > 二手文章。
2. **检索渠道**：通用搜索引擎；GitHub（按 star 数与最近提交时间筛选）；Hugging Face（模型卡里有许可证）；Civitai（风格模型与 LoRA，注意许可证）；arXiv / Papers with Code；YouTube 教程；Reddit（r/gamedev、r/StableDiffusion、r/godot 等）；官方 Discord 或论坛；中文社区（知乎、B 站、CSDN、GameRes 等）。
3. **双语检索**：中英文关键词都要搜，两边结果差异很大。
4. **交叉验证**：关键结论（授权、功能是否存在）至少两个来源一致，或以官方来源为准。
5. **时效性**：记录每条资料的发布或更新时间。超过 2 年的工具信息要再核实现状。
6. **记录格式**：每个工具/方案一张卡片（模板见附录 A），存放在 `docs/research/cards/`。

## 6. 阶段 2：选型与 POC

### 6.1 选型评估（加权打分，写入 DECISIONS.md）

**一票否决**（满足任一条，就不能作为主管线）：

- 既无法用脚本生成或读取动画数据，也无法无头渲染预览；
- 许可证禁止本任务的用途。

**加权打分**：每个维度打 1–5 分（1 = 不支持，3 = 部分支持或需要绕行，5 = 原生完整支持），加权求和。

| 维度 | 权重 | 说明 |
|---|---|---|
| Agent 可自动化程度 | 25% | 能否用脚本生成或修改骨架与动画数据，能否命令行导出，能否无头渲染预览 |
| 质量可验证性 | 20% | 能否逐帧采样骨骼世界变换，以供质检脚本使用 |
| 动画能力 | 20% | 网格变形、权重、IK、约束、事件、皮肤切换 |
| 授权与成本 | 15% | 是否需要付费，许可证是否允许本项目的非商业用途（见第 2 节） |
| 引擎/运行时覆盖 | 8% | Unity / Godot / Cocos / Web 等 |
| 行业成熟度与资料丰富度 | 7% | 出问题时能否查到答案 |
| 后续可持续性 | 5% | 项目是否仍在维护 |

如果两个方案的总分差距小于 0.3，优先选择 POC 中实际跑通、遇到问题更少的那个。

### 6.2 管线形态

必须确定一个 **主管线**，以及至少一个 **完全免费/开源的备选管线**（防止授权受阻）。典型的管线形态如下，具体以调研结论为准：

```
文生图(设定图) → 一致性锁定(LoRA/参考图) → 标准姿势部件生成/拆分 → 抠图与补画
→ 部件规范化(尺寸/命名/锚点) → 骨架模板实例化 → 绑定(含网格/权重)
→ 动画生成(姿势库+曲线/参考视频驱动+人工规则) → 自动质检 → 渲染预览 → 迭代
→ 导出(引擎可用格式 + 图集)
```

### 6.3 POC 内容

用最简单的素材（甚至可以是几何占位图）完成：一个 5–8 根骨骼的人形，一个 idle 循环，导出，能在预览器中播放。

再写一个**最小数据解析脚本**：能按时间采样，输出每根骨骼的世界坐标与旋转。完整的自动质检放到阶段 5 实现，这个脚本就是它的地基。

### Gate 2

POC 全链路跑通，有预览视频。最小解析脚本能输出逐帧骨骼变换，并且与预览画面对得上。选型决策已记录。

## 7. 阶段 3：美术生产规范与生图管线（D3）

### 7.1 规范必须包含的内容

1. **风格定义**：美术风格描述、线条（有无描边、粗细）、上色方式（平涂/赛璐璐/厚涂）、光源方向（全项目统一，例如左上 45°）、色板约束。每种风格都要配风格参考图。
2. **视角**：统一规定。例如横版游戏用纯侧视或 3/4 侧视；俯视角游戏另行规定。同一项目禁止混用视角。
3. **比例与尺寸**：
   - 头身比（默认值见 2.1，全项目统一）；
   - 角色基准高度（像素）、画布尺寸、像素/游戏单位比；
   - 部件最小分辨率；
   - 同一项目内所有角色按统一比例尺出图，禁止各自缩放。
4. **标准绑定姿势**：中立站姿（A-pose 或侧视自然站立），四肢不交叉、不遮挡躯干，手指张开或自然半握（二选一），嘴闭，眼睛睁开。用 ControlNet 骨架图锁定这个姿势。
5. **拆件清单**：每类原型一份，见第 8 节骨架。以人形为例，最少包括：

   头、（可选）头发前/后、脸部表情件、颈、胸、腹/腰、骨盆、上臂 L/R、前臂 L/R、手 L/R（可含多种手型：握、张、指）、大腿 L/R、小腿 L/R、脚 L/R、武器、披风/飘带等附件。

6. **拆件绘制规则**（质量关键）：
   - 关节处必须有 **重叠延伸区**：上臂末端要画成圆头，延伸到肘部以下，前臂起点也要圆头盖住肘部。这样关节旋转 0–150° 时不会露出缝隙或断口。
   - 被遮挡区域必须 **补画完整**：比如被手臂挡住的躯干部分，要画全。
   - 每个部件 **独立透明 PNG**：边缘干净，没有残留背景色，没有半透明脏边（必要时处理预乘 Alpha）。
   - 部件 **不能自带投影、地面阴影或强烈环境光**。阴影交给运行时或单独的阴影件。
   - 左右对称部件可以复用镜像，但光源方向要一致。镜像后光源反了的情况要处理。
   - 每个部件标注 **旋转锚点**（关节中心）。用配套的 JSON 记录锚点坐标。
7. **命名规范**：
   - 文件名格式为 `<角色id>_<部位>[_<侧别l/r>]_<变体>.png`，例如 `hero01_forearm_l_default.png`。全小写，用下划线分隔。侧别后缀与骨骼命名一致。
   - 部件与骨骼**不要求一一对应**：一根骨骼下可以挂多个可切换的图片（例如多种手型）；一张网格图片也可以受多根骨骼的权重影响（例如躯干）。
   - 对应关系统一记录在每个角色的 `rig_map.json` 中，格式为「骨骼 → 显示槽位 → 图片/网格附件 → 权重骨骼列表」。
8. **导出规范**：格式、色彩空间（sRGB）、图集打包参数（padding、是否允许旋转、最大尺寸）、多分辨率策略。
9. **Prompt 模板库**：设定图、三视图、标准姿势全身、单部件、表情件、怪物各原型。每个模板都含正向词、负向词、推荐参数、ControlNet 设置、示例输出。
10. **生图质检清单**：手指数量与形态、肢体数量、左右是否错乱、比例是否符合规范、视角一致、风格一致（与基准图对比）、透明边缘、无文字或水印、无被裁切的肢体、关节重叠区足够、锚点合理。

### 7.2 拆件生产的推荐策略（需在 POC 中比较后选定）

- **策略 1：整图生成 → 自动分割 → 补画被遮挡部分 → 人工规则修整。** 风格一致性最好，补画难度大。
- **策略 2：先生成设定图，再以设定图为参考逐部件生成。** 部件完整，但需要强一致性控制。
- **策略 3：使用分层生成模型直接输出分层结果。** 如果调研发现成熟方案，优先评估。
- **策略 4：混合。** 主体用策略 1，问题部件（手、关节）用策略 2 重绘。

对每种策略记录：一致性、拼合缝隙、耗时、成功率，并选出默认策略。

### 7.3 一致性控制

- 每个角色先产出一张 **基准设定图（Master Reference）**，后续所有部件和变体都以它为参照。
- 优先用参考图控制（IP-Adapter 类）+ 固定种子。如果一致性仍不足，再训练角色 LoRA。
- 每个角色建 `assets/<id>/concept/manifest.json`，记录所有生成参数和原始输出，确保可追溯（见第 2 节第 3 条）。

### Gate 3

至少 1 个人形角色的全套部件通过生图质检清单。拼合为标准姿势后，与基准设定图并排对比，没有明显差异，关节处没有缝隙。

## 8. 阶段 4：骨骼绑定规范（D4）

### 8.1 通用规则

1. **层级**：`root`（位于两脚之间的地面投影点，不做动画或只做位移）→ `hip`（重心骨，躯干与腿的父级）→ 躯干链 / 腿链。手臂挂在胸骨上，头挂在颈骨上。
2. **命名**：小写 + 下划线，侧别后缀 `_l` / `_r`。骨骼与部件的对应关系见 `rig_map.json`（7.1 第 7 条）。附加骨用前缀标识，例如 IK 目标用 `ik_`，约束用 `ctrl_`。
3. **骨骼方向**：骨骼沿肢体方向从父关节指向子关节，骨长等于关节间距。
4. **默认禁止对肢体骨做非等比缩放或长度缩放**。只有规范允许的弹性部位（软体、尾巴、特效）和明确的挤压拉伸镜头才可以缩放，并且要在动画规范中声明。
5. **IK**：腿部默认使用 IK 加脚部目标，用于脚踩地锁定；手臂按需使用。必须固定 IK 弯曲方向（膝盖朝前、肘朝后），防止 IK 翻转。
6. **网格变形**：躯干、衣摆、头发、披风、软体怪物等需要柔性变形的部件用网格 + 权重；刚性部件（武器、盔甲片）不用网格。
7. **绘制顺序（Draw Order）**：规定默认层序（例如后手臂 < 后腿 < 躯干 < 前腿 < 头 < 前手臂 < 武器）。动画中需要换层时，必须用显式的 draw order 关键帧，并写入动画规范。
8. **每类原型一个骨架模板文件**（`pipeline/rig/templates/`），新角色通过脚本实例化：读部件锚点 JSON，自动生成骨架。模板在第一次制作该原型的 Demo 时创建，并且必须通过**模板最小验证**：
   - 能在选定工具或运行时中加载；
   - `rig_map.json` 中的映射完整；
   - 各关节弯曲方向正确；
   - 极限姿势测试无缝隙、无撕裂；
   - 能正常导出。

   只有文件、没有通过验证的模板不算完成。

### 8.2 原型骨架

骨架按**生物形态**分为 5 类。「Boss」不是独立的形态，而是一个**复杂度标签**：任何形态都可以是 Boss，它在所属形态骨架的基础上增加要求，例如部件更多、允许多组子骨架、部件可分离、有阶段切换。

| 原型 | 示例 | 骨架要点 |
|---|---|---|
| 人形 Humanoid | 剑士、法师、哥布林 | 标准人体链，约 18–30 骨 |
| 四足 Quadruped | 狼、野猪 | 脊柱链、颈头链、四腿各 3–4 节（注意趾行动物后腿「反关节」实为踝关节）、尾链 |
| 飞行 Winged | 蝙蝠、鸟妖、小龙 | 翅膀骨（肱/前臂/掌/指膜分区）、身体悬浮重心、可选腿 |
| 多足/节肢 Multi-leg | 蜘蛛、蝎子、甲虫 | 身体主骨 + 每腿 3 节，步态相位规则 |
| 软体/无骨 Blob | 史莱姆、触手怪 | 少量控制骨 + 高密度网格权重，或触手骨链 |

### 8.3 关节角度限制（核心：防止反常识动作）

**不要直接比较骨骼的局部旋转数值**。不同骨架的初始方向可能不同，同一个视觉上的屈膝，在两套骨架里可能对应完全不同的局部角度。统一按以下方式定义和检查：

1. **以绑定姿势为基准**：每套骨架记录绑定姿势（bind pose）。关节角度指的是「相邻两节骨段在世界空间中的相对弯曲角，减去绑定姿势中的同一夹角」。
2. **弯曲方向用符号表示**：每个铰链关节记录 `bend_sign`（+1 或 −1），表示正常弯曲时角度变化的方向。左右侧关节各自记录，不要假设镜像后符号不变。
3. 以上信息写在每个角色的 `joint_limits.json` 中，内容包括：关节由哪两节骨段组成、关节类型、`bend_sign`、允许范围、规则放宽项。质检工具读取这个文件进行检查。

下表是人形侧视的示例起点，角度相对于自然伸直的姿势。你需要结合解剖学资料和参考视频校准，并在规范中说明依据。

| 关节 | 类型 | 允许范围（示例） | 关键约束 |
|---|---|---|---|
| 颈 | 球窝（2D 简化为旋转） | 前屈约 45°，后伸约 45° | 头不能转过躯干背侧 |
| 脊柱各节 | 分布式 | 每节 ±15–25° | 弯曲应分布到多节，不要集中在一节 |
| 肩 | 球窝 | 很大，但手臂不能穿过躯干中心线 | 注意前后手臂层序 |
| 肘 | **铰链** | 0°（伸直）～ 约 145°（屈） | **只能单向弯曲，禁止反折超过约 5°** |
| 腕 | 椭圆关节 | 屈约 70°，伸约 60° | 不能整手 180° 翻折 |
| 髋 | 球窝 | 前屈约 120°，后伸约 30° | 后伸幅度远小于前屈 |
| 膝 | **铰链** | 0° ～ 约 140°（向后屈） | **只能向后弯，禁止反折** |
| 踝 | 铰链 | 背屈约 20°，跖屈约 50° | 着地时脚底须贴地 |

额外规则：

- 怪物的特殊关节（例如趾行动物后肢、昆虫腿）必须单独定义弯曲方向，并配上参考图依据。
- 夸张卡通风格允许放宽的部分，必须在规范中 **显式列出**：放宽了哪些关节、放宽多少、只在哪些动画里允许。未列出即视为不允许。
- 铰链关节禁止反折、骨长不变，属于**硬约束**。各关节的具体角度范围是经过校准的参考值：超出范围时，质检判为错误；如果确属合理的风格化动作，就在 `qa_exceptions` 中声明并说明理由（见 9.4）。

### Gate 4

- `RIG_SPEC.md` 写完 5 类原型的骨架定义和关节规则（文字与表格即可）。
- 人形骨架模板通过 8.1 第 8 条的模板最小验证，第一个人形角色完成绑定。
- 完成**极限姿势测试**：每个关节都转到允许范围的两端，确认无缝隙、无撕裂、层序正确，并截图存档。

其他原型的模板，在阶段 6 制作对应 Demo 时再创建和验证。

## 9. 阶段 5：动画规范（D5）与质检工具（D6）

### 9.1 动画清单（Demo 矩阵）

每个 Demo 角色至少要做下表中适用的动画。命名统一为小写下划线。Boss 列表示 Boss 在其所属形态的动画清单之外，还要额外满足的要求。

| 类别 | 动画 | 人形 | 四足 | 飞行 | 多足 | 软体 | Boss（附加） |
|---|---|---|---|---|---|---|---|
| 待机 | `idle`（循环） | ✔ | ✔ | ✔（悬停） | ✔ | ✔ | ✔ |
| 移动 | `walk`（循环） | ✔ | ✔ | — | ✔ | ✔（蠕动/弹跳） | ✔ |
| 移动 | `run`（循环） | ✔ | ✔（奔跑步态） | `fly`（循环） | ✔ | — | 可选 |
| 跳跃 | `jump_start` / `jump_air` / `jump_fall` / `jump_land` | ✔ | 可选 | — | — | ✔ | — |
| 攻击 | `attack_light`、`attack_heavy` | ✔ | ✔（扑咬） | ✔（俯冲） | ✔ | ✔ | ✔（≥2 种） |
| 技能 | `cast` / `skill` | ✔ | — | 可选 | — | — | ✔ |
| 受击 | `hit` | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |
| 死亡 | `death` | ✔ | ✔ | ✔（坠落） | ✔ | ✔ | ✔ |
| 其他 | `block`、`dash`、`spawn`、`victory` | 至少 2 个 | `spawn` | `spawn` | — | `spawn`（分裂/出现） | `phase_change` |

### 9.2 动画通用技术规范

- 帧率与坐标约定见 2.1。各动画时长有参考范围，例如 idle 1.5–3s，walk 一个周期 0.8–1.2s，attack_light 0.3–0.6s。
- **循环动画（硬约束）**：循环播放时，回到开头的那一刻，姿势和运动速度都必须连续。注意不要把首帧复制到末尾再一起播放，否则接缝处会停顿一帧。
- **位移方式**：项目默认原地动画，由游戏逻辑负责位移，并在 `anim_meta.json` 中填写对应的移动速度。个别动作（冲刺、扑击等）可以声明使用根骨位移。每个动画的位移方式都必须写明。
- **事件**：`footstep`（脚着地帧）、`hit`（攻击判定帧）、`fx_spawn`、`sfx`，位置与命名都要规范。
- 曲线：默认使用缓入缓出（贝塞尔）。线性插值只用于机械运动。禁止全部关键帧使用默认曲线导致动作「飘」。

### 9.3 动作设计规则

每条规则都标了约束等级（定义见第 0 节第 6 条）。

1. **【硬】着地脚锁定**：在标注的接触区间内，经过移动速度补偿后，脚不能滑动，也不能穿地或浮空。
2. **【硬】走跑支撑关系**：走路时始终至少有一只脚着地；跑步有腾空阶段。
3. **【软】走/跑循环关键姿势**：Contact → Down → Passing → Up 四个关键姿势，左右各一次。手臂与同侧腿反相摆动。
4. **【软】重心**：静止和慢速动作中，身体主体（可近似为 hip 加躯干的投影）应位于支撑面之上，摔倒、跳跃时除外。这只是近似判断：持重武器、尾巴很长的角色会有偏差，所以质检只报警告。
5. **【软】攻击节奏**：预备 → 出招（快）→ 命中停顿（可选）→ 跟随 → 恢复。预备通常与出招方向相反，但快速刺击、轻攻击可以弱化或省略预备。
6. **【建议】跟随与重叠**：头发、披风、尾巴、翅膀末端、挂件比主体的运动稍晚，幅度逐级衰减。延迟量按时间而不是帧数衡量，通常在 0.05–0.15s 之间，部件越重、越长，延迟越大。可以先用程序化方法（弹簧、延迟）生成，再微调。
7. **【建议】轨迹**：挥砍、摆臂等动作，手、脚、武器尖端的轨迹应呈平滑弧线；刺击、机械运动可以走直线。关键是避免无意义的折线和抖动。
8. **【软】受击与死亡**：受击反应方向与受力方向一致；死亡的最终姿势要贴合地面，不浮空、不穿地。
9. **【软】多足步态**：
   - 四足：按 walk / trot / gallop 等步态的相位关系安排四条腿的落地顺序；
   - 六足昆虫：可以用交替三脚架步态；
   - 八足（蜘蛛）：通常用交替四足步态，或者从后往前的波浪式步态。
   具体步序要参照参考视频确认，并写入规范。
10. **【建议】参考驱动**：找到真人或动物参考视频（必须授权可用，或者仅作分析、不分发），用姿态估计提取关节角度曲线，作为关键帧的初值或校验基准，再按风格夸张化。

### 9.4 自动化质检工具（D6）

#### 9.4.1 质检所需的元数据

质检工具不能只读动画数据。像「这一段脚是否着地」「原地跑时地面移动多快」这类信息，动画数据里没有，必须由制作方提供。每个角色和每个动画都要附带下面这些机器可读的元数据。JSON 的具体结构由你设计，写入 `ANIM_SPEC.md` 后全项目统一使用。

| 文件 | 必含字段 | 作用 |
|---|---|---|
| `rig_meta.json`（每个角色一份） | `coordinate_system`（坐标方向、单位、角度正方向）、`bind_pose`、`character_height`（H，单位像素）、`ground_y`、支撑点列表（如脚底、蜘蛛的腿尖） | 统一角度基准和尺度 |
| `joint_limits.json`（每个角色一份） | 见 8.3 | 关节检查 |
| `anim_meta.json`（每个动画一项） | `loop`、`root_motion_mode`（原地/根位移）、`locomotion_speed`（原地动画对应的游戏移动速度，单位像素/秒）、`contact_intervals`（每个支撑点的着地时间段）、`required_events`、`qa_exceptions`（允许的例外，必须带理由） | 滑步、循环、事件等检查 |

#### 9.4.2 检查项与默认阈值

阈值统一按角色高度 H 归一化，这样角色大小不同也能用同一套标准。下表中的阈值是**初始值**：允许按实际情况校准，但校准结果要写入 ANIM_SPEC，并重新通过 Gate 5 的正反测试。

| 检查项 | 规则（默认阈值） | 级别 |
|---|---|---|
| 关节极限 | 关节相对弯曲角（按 8.3 定义）超出 `joint_limits.json` 的范围 | 错误 |
| 铰链反折 | 铰链关节向 `bend_sign` 的反方向弯曲超过 5° | 错误 |
| 角度跳变 | 单根骨骼的角速度超过 1440°/s（攻击动画可在例外中放宽），或者插值绕远路（例如 350°→10° 实际转了 340°） | 错误 |
| 骨长变化 | 非弹性骨的世界骨长变化超过 2% | 错误 |
| 脚底滑步 | 接触区间内，支撑点的水平位移（原地动画先扣除 `locomotion_speed` × 时间）超过 0.01H | 错误 |
| 穿地/浮空 | 接触区间内，支撑点与 `ground_y` 的高度差超过 0.01H | 错误 |
| 循环接缝 | 循环动画在回绕处的各骨骼角度差超过 1°，或者回绕处前后的角速度明显不连续 | 错误 |
| IK 翻转 | IK 链的弯曲方向在动画中途翻转 | 错误 |
| 事件缺失 | `required_events` 中的事件缺失 | 错误 |
| 重心越界 | 慢速/静止动画中，身体主体投影长时间离开支撑面（近似判断） | 警告 |
| 静止过久 | 非 idle 动画中，整体运动量过低（动作「死」） | 警告 |
| 关键帧过密/过疏 | 影响可维护性 | 提示 |

- **采样方式**：按固定频率采样（至少 60Hz），并且额外采样所有关键帧时间点和事件时间点，避免漏掉很短的异常。
- **例外处理**：在 `qa_exceptions` 中声明过的例外，不计为错误，但要在报告中单独列出。

输出：

- JSON + Markdown 报告；
- 每个问题标注 骨骼 / 时间 / 数值 / 阈值；
- **问题帧截图**；
- 关节角度随时间变化的曲线图。

另外实现 `tools/qa/render_preview`：输出 MP4/GIF、关键帧联系表（contact sheet）、带骨骼叠加的版本、洋葱皮版本。

### 9.5 视觉质检（主观质量）

自动检查只能发现硬伤。还要做视觉评审：如果你具备多模态能力，就看联系表与视频截帧；否则请求人类评审。如果两者都做不到，就把该动画标记为「未经视觉评审」，在最终报告中列出，然后继续推进。按以下评分表打分（每项 1–5 分）：

1. 姿势可信度（剪影清晰、重心合理）
2. 节奏与时间（预备、停顿、快慢对比）
3. 流畅度（无抖动、无卡顿）
4. 跟随与重叠
5. 角色性格与风格表现
6. 素材拼合（无缝隙、无层序错误、无变形撕裂）

**合格线：自动质检 0 错误，且视觉评分每项 ≥ 3、平均分 ≥ 4。**

### Gate 5

规范文档完成，质检工具通过以下两类测试：

- **反向测试**：人为构造「坏动画」，包括膝盖反折、滑步、首尾不接、包角跳变、骨长拉伸，质检工具必须全部检出。
- **正向测试**：准备至少 2 个合理的动画，例如正常 idle 和原地 walk，质检工具不能误报错误。这一步用来防止检查器过严，或者无论输入什么都报错。

正反测试用例保存在 `tools/qa/tests/`，以后修改检查器或阈值时都要重跑。

## 10. 阶段 6：Demo 批量制作与迭代

### 10.1 Demo 角色建议（具体角色可以调整，完整交付需覆盖全部 5 类生物原型）

1. 人形主角：例如持剑战士，含完整动画集与 2 种手型/武器切换（皮肤/附件切换）
2. 四足怪：例如狼
3. 飞行怪：例如蝙蝠或小型龙
4. 多足怪：例如蜘蛛或甲虫
5. 软体怪：例如史莱姆，主要靠网格变形
6. （加分项）Boss：任选一种形态，多部件的大型怪物

**制作顺序**：人形 → 四足 → 飞行 → 软体 → 多足 → Boss。越往后越可以砍，与第 13 节的降级顺序一致。

### 10.2 单个角色的标准生产流程（每个角色都按此执行并留档）

1. 填写角色需求卡：原型、风格、尺寸、动画清单。
2. 生成基准设定图 → 生图质检。
3. 生成/拆分部件 → 补画 → 规范化（命名、锚点）→ 部件质检。
4. 骨架模板实例化（如果该原型还没有模板，就先创建并通过 8.1 第 8 条的模板最小验证）→ 绑定 → 填写 `rig_meta.json`、`joint_limits.json`、`rig_map.json` → 极限姿势测试。
5. 逐个动画制作：先填写 `anim_meta.json` → 关键姿势（Blocking）→ 自动质检 → 中间帧与曲线（Spline）→ 跟随重叠 → 自动质检 → 视觉评分。
6. 导出 → 在预览器中验证 → 归档 QA 报告。
7. 更新 `PROGRESS.md`，并把遇到的新问题与解法写入故障排查文档。

### 10.3 迭代提升质量的方法

- **小步快跑**：每个动画先做 Blocking（只有关键姿势），通过检查后再细化。不要一次生成完整动画再去整体修。
- **生成—验证—修复闭环**：每次修改后都必须重跑自动质检与预览渲染，禁止「改了没验」。
- **对照参考**：把动画与参考视频或经典关键姿势图并排渲染比较。
- **一次只改一个变量**：生图参数、骨架、曲线分开调整，便于定位问题。
- **姿势库与动作模板复用**：合格的动画沉淀为模板（例如人形 walk 的关节角度曲线），新角色先套用模板再微调。
- **回归测试**：规范或骨架模板修改后，重跑所有已完成 Demo 的质检，确认没有引入回退。
- **记录质量趋势**：每个动画每轮迭代的评分与错误数记录到 `assets/<id>/qa/history.csv`，确认质量在收敛。
- **迭代上限**：同一问题连续修 3 轮没有改善，就换策略（见第 12 节），不要原地重试。

### 10.4 Demo 播放器（D8）

基于选定运行时制作（例如网页运行时或游戏引擎场景），要求：

- 角色列表 + 动画列表切换
- 播放 / 暂停 / 逐帧 / 调速
- 显示骨骼与网格开关
- 地面线与网格背景（便于观察滑步）
- 简单的组合演示：移动中切换攻击，验证动画间混合过渡
- 一条命令即可本地启动，并附带说明

### Gate 6

已完成的每个动画都有 0 错误的 QA 报告、视觉评分达标（或标记为「未经视觉评审」）和预览视频，播放器可运行。Demo 矩阵的完成范围决定最终验收等级（见第 13 节）。

## 12. 问题处理手册

### 12.1 通用处理流程

1. **复现并记录**：现象、输入、环境、日志。
2. **定位环节**：问题出在生图、拆件、绑定、动画、导出、运行时中的哪一个。
3. **查资料**：官方文档 → GitHub Issues → 论坛/社区 → 搜索引擎（英文报错原文 + 工具名 + 版本）。
4. **假设—验证**：一次只验证一个假设。
5. **限时**：单个问题投入超过约 1 小时（或 5 次尝试）仍无进展，就切换到备选方案或降级处理，并记录到 DECISIONS.md。不要卡死在一个点上。
6. **沉淀**：解决后写入 `troubleshooting.md`，格式为「现象 / 原因 / 解法 / 预防」。

### 12.2 常见问题与对策

| 问题 | 可能原因 | 对策 |
|---|---|---|
| 同一角色多次出图风格/长相不一致 | 缺乏一致性控制 | 固定基准设定图 + 参考图控制 + 固定种子；仍不行就训练角色 LoRA；降低随机性参数 |
| 手部畸形、手指数量错误 | 模型通病 | 手作为独立部件单独生成或重绘；使用手部专用 ControlNet/修复流程；准备少量标准手型复用 |
| 姿势不是标准绑定姿势 | Prompt 控制力不足 | 使用 OpenPose/Depth 骨架图强约束；用设定图做图生图 |
| 部件拼合后关节处有缝隙/断口 | 缺重叠延伸区或锚点错误 | 局部重绘扩展部件末端为圆头；重新标定锚点；在极限姿势下复检 |
| 被遮挡部位缺失 | 整图拆分的固有问题 | 局部重绘补画；或改用逐部件生成策略 |
| 抠图边缘有白边/脏边 | 背景残留、预乘 Alpha 问题 | 纯色背景出图 + 高质量抠图模型 + 边缘收缩/去色溢；导出时统一 Alpha 处理方式 |
| 膝/肘反折 | 关键帧角度错误或 IK 弯曲方向翻转 | 固定 IK 弯曲方向；质检定位帧并修正；关键帧角度钳制在限制表内 |
| 旋转「绕远路」（如从 350° 转到 10° 却转了 340°） | 角度包角插值 | 关键帧角度展开（unwrap）为连续值；质检检测 |
| 脚底滑步 | 腿部 FK 动画与身体位移不同步 | 腿部改用 IK + 脚部目标锁定；原地动画按地速补偿 |
| 动作「飘」、没重量感 | 线性/均匀节奏，缺预备和停顿 | 套用节奏规则：预备、快出、停顿、缓收；增加重心上下起伏 |
| 网格变形撕裂/扭曲 | 网格过稀、权重不平滑 | 关节处加密网格；平滑权重；限制该部位旋转幅度 |
| 层序错误（手臂穿到身体后面） | Draw order 未按动画切换 | 加显式 draw order 关键帧；规范默认层序 |
| 选定工具需要付费授权/账号 | 授权限制 | 请求人类决策；同时推进开源备选管线 |
| 工具只有 GUI，无法自动化 | 工具限制 | 优先改为直接生成其公开数据格式；或用开源编辑器/引擎替代；GUI 自动化只作最后手段 |
| 本地显存不足以跑生图模型 | 硬件限制 | 使用量化/轻量模型、降低分辨率后放大、或改用云端 API（需人类授权） |
| 找不到成熟方案（例如自动分层） | 领域仍不成熟 | 记录调研结论；采用半自动方案并把人工介入步骤标准化写入规范 |
| 检索结果互相矛盾 | 信息过时或来源不可靠 | 以官方最新文档为准，并实际动手小测试验证 |

### 12.3 何时必须请求人类

仅限 2.1 列出的几种情况。风格、头身比等主观问题，使用 2.1 的默认值自主决定，不需要请求人类。

请求时附上：问题描述、已尝试方案、可选项及各自影响、你的推荐。同时继续推进不受阻塞的工作。

## 13. 降级规则与验收等级

### 13.1 取舍优先级

当时间或资源不足时，按以下优先级取舍（越靠前越不能砍）：

1. 规范文档（ART / RIG / ANIM SPEC）与关节限制
2. 自动化质检工具（含正反测试）
3. 人形角色完整动画集
4. 至少 2 类怪物原型的核心动画（idle、移动、attack、hit、death）
5. Skill 文档与验证
6. 其余怪物原型、加分动画、Boss
7. 播放器的高级功能

任何降级都必须写入 DECISIONS.md 与 FINAL_REPORT.md 的「已知限制」。

### 13.2 验收等级

| 等级 | 条件 |
|---|---|
| **完整通过** | D1–D10 全部达标；Demo 覆盖全部 5 类生物原型及其完整动画清单；Skill 通过 11.3 的验证 |
| **降级通过** | D1–D6、D9、D10 达标；Demo 至少包含人形完整动画集，以及 2 类怪物原型的核心动画；播放器能播放、能切换动画；Skill 至少完成文档编写，并做过一次验证（哪怕只验证到绑定那一步）；所有未完成项都在报告中列明 |
| **未通过** | 达不到降级通过的条件，或者存在虚报（声称完成但没有证据） |

目标是完整通过。降级通过是允许的结果，但必须如实说明。
